2. Planteamiento del Problema

Limitaciones de SQL Relacional

En el sector industrial, agrícola y de seguridad, la operación de flotas de drones requiere planificar rutas complejas de vuelo (misiones) y monitorear variables de salud y ubicación de los vehículos en tiempo real (telemetría). Las bases de datos relacionales tradicionales (SQL) enfrentan severas limitaciones en este escenario debido a:

PUNTO 1

Atributos de Ruta Heterogéneos

Cada punto de navegación (waypoint) exige tareas de naturaleza distinta. Por ejemplo:

  • Capturar foto: Parámetros de cámara RGB, ISO, tiempo de exposición, apertura, ángulo del gimbal, ráfaga.
  • Medir sensores térmicos: Paleta radiométrica, emisividad superficial, umbral de alarma en °C, grabación de stream FLIR.
  • Pausar o realizar giros 360°: Tiempo de hover estacionario, velocidad angular en grados/segundo, solapamiento panorámico.
  • Escaneo multiespectral: Bandas espectrales (NDVI, RedEdge, NIR), calibración de reflectancia solar.
En SQL tradicional: Obligaría a crear una tabla gigante con decenas de columnas donde el 90% son NULL, o diseñar múltiples tablas relacionales normalizadas que exigen costosos JOINs para reconstruir una sola ruta.
Solución en MongoDB: Cada waypoint es un subdocumento BSON polimórfico anidado dentro de la colección missions. Almacena exactamente los campos que necesita sin restricciones de esquema rígido.
PUNTO 2

Volumen de Telemetría en Serie Temporal

El envío continuo de ráfagas de datos durante el vuelo (ubicación GPS, altitud, velocidad, nivel de batería, temperatura y voltaje) exige escribir lecturas frecuentes con sellos de tiempo (timestamps).

  • Alta Frecuencia: Ráfagas de 5Hz a 20Hz por dron en flotas concurrentes simultáneas.
  • Sellos Temporales Precisos: Índices ordenados por timestamp e identificador de misión.
  • Patrón Append-Only: Los registros de telemetría son inmutables; se insertan continuamente sin actualizaciones destructivas.
En SQL tradicional: Los motores ACID relacionales con bloqueos de tabla/página y comprobaciones estrictas de llaves foráneas sufren cuellos de botella ante escrituras de ráfagas masivas en tiempo real.
Solución en MongoDB: Motor optimizado para escrituras masivas directas con PyMongo (insert_one / insert_many), soporte de colecciones Time-Series y agregaciones eficientes con Pipeline ($bucket, $group, $avg).

3. Usuarios Principales y Casos de Uso

Roles del Sistema

Operador de Vuelo

Responsable del diseño táctico de rutas, configuración de tareas por waypoint, despegue y supervisión en tiempo real de los instrumentos de vuelo.

• Diseña misiones asignando waypoints en mapa interactivo.
• Define configuraciones de tareas heterogéneas por punto de control.
• Ejecuta la misión y monitorea la ruta en vivo con telemetría HUD.

Evidencia Técnica para Evaluación
[!] Modelo SQL Relacional (Rígido, Múltiples Tablas y Columnas Nulas) 
-- SQL requiere fragmentar cada tarea en tablas separadas:
CREATE TABLE missions (
    id INT PRIMARY KEY,
    name VARCHAR(255),
    sector VARCHAR(50)
);

CREATE TABLE waypoints (
    id INT PRIMARY KEY,
    mission_id INT REFERENCES missions(id),
    lat DECIMAL(9,6),
    lng DECIMAL(9,6),
    action_type VARCHAR(50)
);

-- Tablas hijas con relaciones 1-a-1 o columnas nulas:
CREATE TABLE waypoint_photo_tasks (
    waypoint_id INT REFERENCES waypoints(id),
    camera VARCHAR(50),
    iso INT,
    shutter VARCHAR(20),
    gimbal_pitch INT
);

CREATE TABLE waypoint_thermal_tasks (
    waypoint_id INT REFERENCES waypoints(id),
    palette VARCHAR(50),
    emissivity DECIMAL(3,2),
    temp_alarm DECIMAL(5,2)
);

-- Para leer 1 ruta: Múltiples LEFT JOINs pesados:
SELECT * FROM missions m
JOIN waypoints w ON m.id = w.mission_id
LEFT JOIN waypoint_photo_tasks p ON w.id = p.waypoint_id
LEFT JOIN waypoint_thermal_tasks t ON w.id = t.waypoint_id;
[✓] Modelo MongoDB BSON (Documento Único con Subdocumentos Embebidos)
